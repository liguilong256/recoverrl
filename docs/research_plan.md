# RecoverRL 研究计划

## 问题

工具调用失败后，Agent 往往只能看到超时，无法知道请求是未执行、已执行还是仍在执行。这个项目研究模型能否结合工具契约与后续观察，完成恢复，并减少重复写入、查询和等待。

第一轮实验验证两个假设：

1. 在相同 SFT 初始化与训练预算下，对实际副作用计分，比只奖励完成任务更能减少重复执行。
2. 加入调用和等待成本后，策略能够根据契约选择恢复方式，并迁移到未训练过的依赖结构与延迟范围。

这两个假设都可能不成立。GRPO 是现成算法，当前奖励也是可解释的加权和；贡献要由对照和消融结果支撑。已有工具学习与执行核验研究见[相关工作](experiment_protocol.md#related-work)。

## 本轮已经实现

- 按实际写入账本评分的模拟工单服务，支持幂等键、部分提交、延迟提交与读可见性延迟。
- 故障目标在任务中随机选择，可以出现在任务中途的步骤；每个 episode 仍只有一个故障。
- 四个独立测试集，分别测模板内、工作流、时间契约及二者联合迁移。
- `verify` 等到已知上界后查询；`query_first` 先查已完成操作，只有等到上界后才根据空结果重试。两者都只读取公开信息。
- 训练数据与 SFT 示范生成、固定数据校验值、顺序实验调度、按种子保存结果、配对比较和报告导出。

原来的 `recoverrl generate` 继续用于小规模环境自检。正式实验使用 `recoverrl.study prepare`，不要混用两套结果。

## 数据划分

所有任务均有 4–6 个目标。每个基础任务展开成 5 种故障状态 × 4 种工具契约，共 20 个 episode；无故障样本占 20%。同一任务的隐藏故障变化不会改变初始提示词。

| 集合 | 基础任务 / episode | 依赖结构 | 提交上界 / 读延迟 |
| --- | ---: | --- | --- |
| train | 256 / 5,120 | batch、chain、fanout | 2 或 4 / 0 或 1 |
| val | 32 / 640 | 同训练结构，新任务 | 同训练范围 |
| test_id | 64 / 1,280 | 同训练结构，新任务 | 同训练范围 |
| test_workflow | 64 / 1,280 | diamond、随机 DAG，包含多父节点 | 同训练范围 |
| test_timing | 64 / 1,280 | 同训练结构，新任务 | 8 或 12 / 3 或 6 |
| test_joint | 64 / 1,280 | diamond、随机 DAG | 8 或 12 / 3 或 6 |

实际提交延迟在各自的上界内采样，训练和测试的目标标识互不重叠。工作流迁移保持目标数量与时间范围不变；时间迁移保持结构集合不变。各测试集是独立任务，方法间在同一测试集上配对；不同测试集之间不做配对差值。

测试集仍然属于同一个合成服务，不代表跨 API 或真实业务泛化。部分提交作用于实际调用批次；单项调用时，它与提交后丢失响应等价。第二个故障、取消操作和补偿操作留作下一轮扩展，不计入本轮结论。

## 对照与消融

| 条件 | 用途 |
| --- | --- |
| Base | 检查原模型的格式遵循和恢复能力 |
| SFT | 判断规则示范本身能学到多少 |
| Completion GRPO | 只奖励完成任务 |
| Constrained GRPO | 完成奖励减去重复、额外写入和成本 |
| No duplicate penalty | 单独移除重复写入惩罚 |
| No cost penalty | 同时移除调用与等待成本 |
| verify / query_first | 同等公开信息下的领域规则参考 |

SFT 使用训练集中的 `query_first` 成功轨迹，相同对话只保留一次。所有 RL 条件从同一个 SFT checkpoint 开始，各跑 42、43、44 三个种子，每次 200 次更新、batch 16、每提示 4 条 rollout。种子实验衡量固定 SFT 初始化后的 RL 变化，不包含 SFT 重训方差。先跑主对照，再决定是否投入六次消融。

评测统一 greedy 解码、每轮最多 512 个生成 token、24 次环境调用，以及总响应/观察预算 6,144 token。所有模型使用相同 tokenizer 与服务配置。HTTP 评测重编码历史，RL 保留实际生成 token，因此记录两条路径的预算方式，仍须在服务器检查 tokenizer 对齐和截断率。

## 怎么判断结果

主指标是 `exact_success`：请求全部完成，且没有重复或额外写入。同时报告普通完成率、重复率、平均调用、等待、无效动作、生成 token 和预算耗尽率。所有成本都包含失败任务。

分别查看无故障与各类故障、是否支持幂等键，以及四个测试集。先检查减少重复是否只是靠提前放弃；再检查降低成本是否来自更多失败。只在这些指标一起支持时讨论改善。

配对 bootstrap 按基础任务聚类；三个训练种子分别列出，不把所有 episode 拼在一起当作独立样本。最终同时报告种子间均值与范围。调参只用 val，确定 checkpoint 选择规则之后再跑四个测试集。

现有脚本结果中，两个强规则都达到 100% exact success。`query_first` 在延迟迁移集上平均少等待 1.2 tick，但多调用 0.4 次，体现了不同成本之间的取舍。这里的 tick 是模拟时间，不是实测服务延迟。RL 是否能做得更好，目前没有结果。

## 8–10 周安排

| 时间 | 工作 | 产物 |
| --- | --- | --- |
| 第 1 周 | 安装 GPU 依赖、基础模型 val 评测、完成一次 GRPO 更新 | 环境版本、显存与耗时记录、失败轨迹 |
| 第 2 周 | SFT，检查格式错误、响应 mask 和各故障分项 | SFT checkpoint 与 val 报告 |
| 第 3–4 周 | 两个主条件各三个种子 | 训练曲线、checkpoint、val 对照 |
| 第 5–6 周 | 重复惩罚和成本消融；根据实测吞吐调整后续规模 | 六次消融结果、奖励与成本分析 |
| 第 7–8 周 | 固定选择规则，执行最终测试和错误分类 | 配对统计、各测试集结果、典型成功与失败轨迹 |
| 第 9–10 周 | 根据结果决定扩大到第二种工具，或整理负结果与可复现实验 | 技术报告、复现命令与 GitHub release |

如果第一个更新都无法稳定完成，先修训练与资源配置。若 SFT 已解决问题而 RL 没有收益，就如实报告；若规则一直更有效，应分析工具契约覆盖范围与调用成本，不通过削弱规则或只展示容易的样本制造优势。
